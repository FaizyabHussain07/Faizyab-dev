This is a working note about a decision I made in [PasteLink Pro](https://paste-link-pro.vercel.app/), and about the part of it that is easy to overstate.

## The decision

PasteLink Pro lets someone protect a link with a password. The password is hashed with SHA-256 **in the browser**, and only the hash is ever sent to the server. The server stores the hash, and compares it against the hash of whatever password is typed on the viewing side.

```js
async function hashPassword(password) {
  const data = new TextEncoder().encode(password)
  const digest = await crypto.subtle.digest('SHA-256', data)
  return Array.from(new Uint8Array(digest))
    .map((byte) => byte.toString(16).padStart(2, '0'))
    .join('')
}
```

That is the whole mechanism. There is no server-side hashing step, because the server never sees the plaintext.

## Why it is worth doing

The obvious benefit is that the plaintext password is not in transit, not in logs, and not in the database. If the store is ever exposed, what leaks is a set of hashes rather than a set of passwords.

There is a second benefit that matters more in practice: **the server cannot read the content it is protecting**.

The paste itself is stored in Redis, in the clear, until it expires. The password gates access to that content. Because the gate is a hash comparison rather than a decryption key, nobody reading the database can use it to recover the content, because there is no key to recover.

That is the honest version of the "zero-knowledge" framing. It is a property of the *access control*, not an encryption scheme for the content.

## What it does not do

It is worth being precise about the limits, because this is the part that is usually glossed over.

- **SHA-256 is fast.** That is exactly what you want for a content-addressing hash, and exactly what you do not want for a password hash. A fast hash lets an attacker who has the stored hash try large numbers of candidate passwords quickly. For a shared secret that a human chose, a slow, salted KDF such as Argon2 or scrypt is the better tool.
- **There is no salt.** Every paste of "hunter2" produces the same hash. A database-wide rainbow table becomes viable.
- **The content is not encrypted.** It sits in Redis in plain text until its TTL expires. If the store is compromised, the content is exposed regardless of the password.

None of that matters much for a ten-minute paste that a developer shares with a colleague. It would matter a great deal if the same mechanism were used to protect a password vault. I do not intend to use it that way, but the distinction is worth making before somebody else copies the pattern.

## The parts I would change

If I rebuilt this today, I would keep the client-side hashing and change two things.

First, a slow KDF in the browser. `crypto.subtle` does not expose Argon2 or scrypt, but the WebCrypto API does support PBKDF2, and PBKDF2 with a high iteration count and a per-paste random salt is a reasonable middle ground that any browser can run.

Second, a per-paste salt stored alongside the hash. It costs one extra field and one extra round trip, and it removes the shared-hash problem entirely.

## The other half of the design

Hashing is only half of it. The Redis token is a server-side environment variable, and the browser never talks to Redis directly. Every read and write goes through a serverless function.

The three functions are the whole backend:

- `save.js` writes the content with a TTL.
- `get.js` reads it back, and deletes it if the password does not match.
- `delete.js` removes it on demand.

Expiry is handled by Redis itself rather than a cleanup job, which means there is no window where a background process has to run for the data to disappear. The trade-off is that a TTL is a promise about storage, not a guarantee about deletion. Once the key is gone, it is gone.

## Why I am writing this down

I rebuilt the security model of this project more than once, and both times the hard part was not the code. It was working out precisely what the design did and did not protect, so that the product description could say something true.

That is the part worth remembering, and the part that is easy to skip when you are three hours into a build and the feature is working.
